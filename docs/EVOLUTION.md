# AdvisorOps Evolution

这份文档记录产品为什么从最初的“客户排序 Demo”演进成当前结构，避免后续重构又把已经解决的问题带回来。

## E0 — 单列表 Priority Demo

最初目标只是回答“今天先联系谁”，所有客户进入一个排序列表。

暴露的问题：

- 已经在处理的客户仍会被重复推荐；
- Relationship Stage、跟进时间、工作状态混在一起；
- 最近联系过的客户只能靠简单扣分避免重复触达；
- 沟通完成后只有字段变化，没有完整历史。

## E1 — 工作区 / 发现区分离

核心变化：

- **工作区**：已经决定处理的客户，关注执行进度；
- **发现区**：当前存在新行动理由、尚未进入执行的客户；
- Priority 只在发现区内部排序。

结果：

- 同一客户不再同时出现在“正在处理”和“建议跟进”；
- “今天手上有什么活”和“下一个应该找谁”成为两个不同问题。

## E2 — Snapshot + Activity + WorkItem

从“只改 Customer 字段”演进到：

- Customer Snapshot：当前已确认状态；
- Activity Event：完整历史事实；
- WorkItem：客户经理当前执行任务；
- Field Change Audit：字段变化来源。

这一步解决了“当前状态能看见，但不知道为什么变成这样”的问题。

## E3 — 时间回流与确定性 Discovery

`next_contact_at` 不再被做成 Relationship Stage，而是按当前时间动态推导 scheduled / due / overdue。

因此：

- 约定未来时间前不打扰；
- 到期自动回到发现区；
- 不依赖凌晨批处理修改客户状态；
- 最近联系不再简单按天数扣分，而是判断是否仍有新的行动理由。

## E4 — 多源 Activity Inbox

引入 Mock CRM、企业微信、行为数据和 cursor/idempotency 语义。

外部事实先进入 Activity；解释性变化进入 Change Proposal，经人工确认后才改 Snapshot。

产品原则稳定为：

> AI 负责理解，规则负责约束，人负责决策。

## E5 — 自然语言与视觉记录

记录客户进展从“大表单”演进成：

文字 / 聊天截图 → 智能整理 → 结果卡 → 人工确认。

原始文字和图片完整保留；结构化字段默认折叠，只有识别错误时才手工修改。

## E6 — 客户全景画像

客户画像从“资产 + 风险 + 意向”扩展到：

- 粗粒度地域、职业、行业；
- 家庭阶段和未来安排；
- 收入、负债、现金流；
- 投资经验、目标、期限；
- 沟通偏好、兴趣、顾虑和信任因素；
- 与事实分离的待验证经营假设。

软画像可以进入摘要和沟通准备，但不直接改变 Priority，避免把模糊心理判断变成黑盒评分。

## E7 — AdvisorOps / GitHub-ready

V0.6 的目标是把项目从个人演示工程收敛成可公开阅读的小型产品仓库：

- 正式命名 **AdvisorOps**；
- 批量 CSV 导入、字段归一化和预览确认；
- 批量删除与级联清理；
- 标准导入模板和示例；
- GitHub CI / Dependabot / Security / Contributing；
- 去掉对相邻本地项目配置的隐式依赖；
- README 重写为产品、架构、运行和边界说明。

## E8 — 客户经营判断

客户详情从“把字段全部展示出来”继续收敛成“先形成经营认知，再展开证据”。

新增第一屏经营判断卡，直接回答：

- 当前状态；
- 真正关注点；
- 决策障碍；
- 下次沟通需要确认的问题；
- 沟通方式；
- 当前应该避免的动作。

这一层不使用额外 LLM 调用，而是从 Current Snapshot、WorkItem、最近 Activity 和画像即时生成，并为每条判断保留 Evidence。待验证假设必须单独标识，最近明确事实优先级高于长期画像。

目标不是替代券商 CRM，而是让项目更能表达对财富管理客户经营、资金需求和沟通边界的理解。

## 当前稳定边界

AdvisorOps 仍然是 **portfolio/demo prototype**，不是券商生产 CRM：

- 全部仓库数据为模拟数据；
- 不接真实券商内部系统；
- 不自动给客户发送投资建议；
- 不把 AI 当权威事实源；
- Priority 是工作顺序，不是成交概率；
- 真实生产化需要单独完成 IAM、权限、审计、数据保留、模型网关和个人信息治理。
